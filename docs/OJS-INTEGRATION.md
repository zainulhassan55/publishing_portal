# OJS integration

## The division of responsibility

OJS 3.5 is a **standalone service** and the **system of record** for everything
in the editorial workflow. The portal is a read model plus a nicer front door.

| Owned by OJS | Owned by the portal |
| --- | --- |
| Users, passwords, roles | Journal proposals |
| Submissions, revisions, files | Email alert subscriptions |
| Review rounds, reviewer assignments, reports | Contact messages |
| Editorial decisions and letters | Wizard drafts (pre-submission only) |
| Issues, galleys, published articles | Portal-only preferences (interests, alert prefs) |
| DOI deposits to Crossref, OAI-PMH | Public presentation, SEO, search |

Two rules follow, and neither is negotiable:

1. **The portal never writes to the OJS database.** Not a single `UPDATE`. All
   interaction is through the OJS REST API or OAI-PMH. A second writer into that
   schema is how submissions get silently corrupted.
2. **The portal never becomes a second account store.** There is one identity,
   and OJS holds it. `user_prefs` keys on `ojs_user_id` and holds only fields
   OJS has no concept of.

Both run on one origin: nginx serves the portal at `/` and OJS at `/ojs`. That
is not an accident of history — it is the thing that makes the auth design below
possible at all.

## Integration ladder

| Surface | Mechanism | Status |
| --- | --- | --- |
| Article, issue, journal pages | Read-only harvest → `content/harvest.json` → static pages | Built (`scripts/harvest.ts`) |
| Search | Build-time index over the same data | Built (`src/lib/search.ts`) |
| Sign in / session | Same-origin OJS session cookie | Built, **unverified** — see spike |
| Wizard steps 1–6, autosave | Portal-native, drafts in the portal DB | Built |
| Final submit | OJS REST, with a designed hand-off fallback | Built, fallback is the safe path |
| Dashboard reads | OJS REST on behalf of the user | Partially built |
| Reviewer workspace, file uploads, revisions | OJS REST | Not built — Phase 4 |
| Editorial back office | Link out to OJS, permanently | By design |

## The auth spike (gate for Phase 3)

This is the one genuinely unknown part of the integration, and it is unknown for
a specific reason: **OJS has no OAuth, and its per-user API keys have to be
generated by hand in the OJS profile.** Neither is usable by an author. What is
left is the session cookie, and using it this way is undocumented.

`src/lib/auth/session.ts` and `src/app/api/auth/sign-in/route.ts` implement the
approach. Before building anything further on top of it, run these four checks
against a staging OJS:

1. **Login relay.** `POST /api/auth/sign-in` with valid credentials. Does OJS
   return a 3xx plus a `Set-Cookie: OJSSID=…`? If it instead re-renders the
   login form with a CSRF complaint, the login handler needs a token fetched
   from the form first.
2. **Session resolution.** With that cookie, does `GET /ojs/index.php/index/api/v1/users/me`
   return the user? A 401 here means the cookie is path- or scope-restricted in
   a way that breaks the whole approach.
3. **Mutating call.** Attempt a real submission create via
   `POST /ojs/index.php/<journal>/api/v1/submissions` with the session cookie. A
   403 is the expected signal that OJS wants an `X-Csrf-Token`; find where that
   token is exposed to a logged-in session and whether it is stable.
4. **Expiry behaviour.** Let the session idle past the OJS timeout. The portal
   must degrade to signed-out, not to a 500 on a public page.

Record the results in this file. **Do not scope the reviewer workspace or the
revision flow until checks 3 and 4 pass.**

### If the spike fails

The fallback is already built and is not a disaster:

- Sign-in links out to the OJS login page.
- The wizard still runs natively with autosaved drafts; `POST /api/drafts/submit`
  returns `{ mode: 'handoff', continueUrl }` and the UI explains that the final
  step completes in OJS.
- The dashboard shows harvest-level status rather than per-user workflow state.

That is one awkward step instead of six, and every piece of it is upgradeable
once the API path is confirmed.

## Harvest

```
OJS_BASE_URL=https://www.nextgeniqpress.com/ojs OJS_API_KEY=… npm run harvest
```

Writes `content/harvest.json`. Run it **before `next build`** in CI, and on a
cron afterwards so publishing in OJS reaches the site without a developer.

Notes:

- Reads use the REST API rather than OAI-PMH. OAI's Dublin Core would lose
  affiliations, ORCIDs and CRediT roles, all of which the article page and the
  Scholar citation tags need.
- `status=3` is `STATUS_PUBLISHED`. Anything else is not public and must not be
  harvested.
- A failed request for any journal exits non-zero. A partial harvest would make
  a journal with articles look like a journal without any, so CI must not
  publish it.
- The snapshot is disposable. Deleting it loses nothing a re-run cannot rebuild,
  which is why it is a file and not a database table.

## OJS-side configuration that must be fixed first

From `docs/PLATFORM-AUDIT.md`. These are OJS or DNS changes, not portal code,
and three of them are time-sensitive.

- **F-02 — OAI identity is `localhost:8000`.** `config.inc.php` has a
  development `base_url`, so the OAI repository identifier is
  `oai:localhost:8000:article/1`. Every harvester that picks this up caches a
  broken identity. **Fix before the first article is published** — afterwards it
  requires re-registration with each service that already harvested.
- **F-11 — session cookie missing `Secure`.** Set `force_ssl = On`.
- **F-07 — DKIM.** Enable DKIM, SPF and DMARC for the sending domain, then move
  OJS SMTP to a provider that reports delivery.
- **F-04 — DOIs.** Crossref membership, then enable the DOI plugin and configure
  the prefix. The site currently advertises "DOI-ready articles" with no deposit
  workflow behind it.
- **F-10 — preservation.** Enable the PKP Preservation Network plugin. DOAJ
  requires a preservation arrangement.
- **F-16 — the `dmpedia` theme is not in version control.** It exists only as
  files on the server; a rebuild or upgrade loses it with no recovery path. Copy
  it into `ojs/theme-dmpedia/` in this repo and deploy it from there.
